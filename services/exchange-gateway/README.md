# OKX Exchange Gateway

Единственная точка интеграции с OKX. Публичные `trades`/`books5` читаются из public WebSocket, свечи — из business WebSocket. REST backfill: `POST /exchange/sync`. По умолчанию автоматическое сетевое подключение выключено (`MARKET_DATA_ENABLED=false`), торговый режим — demo.

## Округление частей take-profit

Для split TP промежуточные части округляются вниз до шага количества OKX.
Если хотя бы одна часть округляется до нуля, вход отклоняется: исходное распределение
по целям не заменяется закрытием всего объёма на одной цели.
Если объёма хватает на все части, сохраняется обычное распределение с остатком на последней цели.

## Частичное исполнение входа

При `PARTIALLY_FILLED` входного ордера gateway сверяет актуальный cumulative fill через REST.
Если вход уже исполнен полностью, принудительный выход не запускается только после подтверждения
активного собственного стопа на тот же инструмент, противоположную сторону и весь исполненный объём
(либо `closeFraction=1`). Если вход остаётся частичным, gateway запрашивает отмену остатка и повторно
читает состояние: исполнение могло завершиться одновременно с отменой. Эта проверка применяется
как к private WebSocket, так и к reconciliation; частичные исполнения выходных ордеров не отменяются.

Неподтверждённое состояние или защита сохраняют `UNPROTECTED_PARTIAL` и блокировку новых входов.
Ошибка первой REST-проверки не отменяет попытку отменить остаток. Проверка не добавляет ожидания
следующего WebSocket-события. Если стоп ещё не виден в REST после полного входа, позиция консервативно
закрывается. В `ORDER_UPDATE` поле `exchange` содержит использованное состояние, а при REST-сверке
`observed_exchange` сохраняет исходное WebSocket-событие.

## TLS и диагностика подключения

Все OKX WebSocket используют отдельный `SSLContext` с минимальной и максимальной версией TLS 1.2.
REST-запросы OKX выполняет отдельный HTTP-клиент с таким же ограничением, включая запросы reconciliation.
Проверка цепочки сертификата и имени сервера включена. Глобальные настройки SSL и HTTP-клиент внутренних
сервисов не изменяются; HTTPX сохраняет обработку proxy/`NO_PROXY`. Дополнительные повторы REST-запросов не добавлены.

Открытие WebSocket ограничено 20 секундами; private login и подтверждение подписки `orders` имеют общий
таймаут 20 секунд. После отключения readiness сбрасывается; reconnect повторяет авторизацию, подписку и
reconciliation с существующей экспоненциальной задержкой. Если initial reconciliation не удался при работающем
канале, существующий reconciliation loop повторяет проверку каждые 30 секунд.

В логах `OKX private WebSocket failed` поле `phase` отличает `connect`, `login/subscribe`, `reconciliation`
и `receive`; отказ авторизации/подписки содержит код OKX без содержимого login payload.
`OKX REST connection failed` содержит host, method, path без query и типы исключений с цепочкой причин
(например, `ConnectTimeout` или `SSLCertVerificationError`), без подписей и заголовков доступа.
При ошибке initial/periodic reconciliation логируется соответствующее исключение.

Успешная публичная подписка сама по себе не означает готовность торговли. При включённой торговле `/health`
остаётся 503 до готовности private `orders`, успешного reconciliation и работающего обработчика команд;
для активных символов также нужны свежие M1-свечи business-канала (менее 120 секунд).
При успехе `/health` возвращает `status: UP`. Ошибки проверки сертификата требуют исправления доверия/сертификата,
а не отключения SSL verification.

## Исторические свечи

`POST /exchange/history` создаёт фоновую задачу. Для каждого ТФ сервис запрашивает официальный OKX endpoint
`/api/v5/market/history-candles` страницами по 300 записей, двигается назад через курсор `after` и пакетно сохраняет только закрытые свечи.
Каждый выбранный таймфрейм выполняется отдельной параллельной подзадачей. Поле `timeframe_status` в ответе содержит статус,
число свечей, число запросов и ошибку отдельно для каждого ТФ.

```json
{
  "symbol": "BTC-USDT-SWAP",
  "timeframes": ["M1", "M5", "M15", "H1", "H4", "D1"],
  "from_timestamp": 1735689600000,
  "to_timestamp": 1787529599000
}
```

Все доступные закрытые свечи внутри периода загружаются без лимита количества. Статус: `GET /exchange/history/{job_id}`. Повторная загрузка безопасна: ключ свечи состоит из символа, ТФ и времени, сохранение использует
upsert. Через API Gateway запуск разрешён только администратору.
`POST /exchange/history` поддерживает полную и инкрементальную загрузку. При `incremental: true` сервис для каждого выбранного
таймфрейма начинает с первой свечи после последней сохранённой и загружает закрытые свечи до `to_timestamp` (обычно текущего времени).
