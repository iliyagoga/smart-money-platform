# Smart Money Platform — Elliott

Платформа анализирует волны Elliott, выполняет исторические бэктесты и управляет
торговыми конфигурациями, портфелями, ордерами и позициями. ML, обучение моделей
и стандартные SMC-стратегии удалены из рабочего контура.

## Полный локальный запуск

Требуются Docker Engine с Compose и свободные локальные порты `3000`, `8050` и
`8080`. Создайте локальный файл окружения:

```bash
cp .env.example .env
```

Перед запуском обязательно замените значения `CHANGE_ME` для
`POSTGRES_PASSWORD`, `REDIS_PASSWORD` и `KEYCLOAK_ADMIN_PASSWORD`. Для локальной
работы оставьте:

```dotenv
ENVIRONMENT=development
PUBLIC_FRONTEND_URL=http://localhost:3000
PUBLIC_API_URL=http://localhost:8050
PUBLIC_KEYCLOAK_URL=http://localhost:8080
PUBLIC_API_HOSTS=localhost,127.0.0.1
DEPLOYMENT_BIND_ADDRESS=127.0.0.1
```

Проверьте конфигурацию, соберите и запустите весь стек:

```bash
docker compose config --quiet
docker compose up -d --build --remove-orphans
docker compose ps
curl http://localhost:8050/health
```

Дождитесь состояния `healthy` у сервисов. После запуска доступны:

- frontend: http://localhost:3000;
- API Gateway: http://localhost:8050;
- Keycloak: http://localhost:8080;
- Keycloak Admin Console: http://localhost:8080/admin/master/console/.

### Первый пользователь и вход

`KEYCLOAK_ADMIN` и `KEYCLOAK_ADMIN_PASSWORD` создают bootstrap-администратора
realm `master`. Эта учётная запись предназначена только для Keycloak Admin Console
и **не может использоваться для входа во frontend**, который работает с realm
`smart-money`. Bootstrap-переменные применяются при первом создании Keycloak;
последующее редактирование `.env` само по себе пароль существующего администратора
не меняет.

Чтобы создать первого пользователя платформы:

1. Откройте Keycloak Admin Console и войдите значениями `KEYCLOAK_ADMIN` и
   `KEYCLOAK_ADMIN_PASSWORD` из `.env`.
2. В левом верхнем списке realm переключитесь с `master` на `smart-money`.
3. Откройте **Users**, нажмите **Create new user**, задайте username и включите
   пользователя.
4. На вкладке **Credentials** задайте пароль. Отключите **Temporary**, если не
   хотите обязательную смену пароля при первом входе.
5. На вкладке **Role mapping** выберите **Assign role**, включите отображение realm
   roles и назначьте одну или несколько ролей `admin`, `trader`, `viewer`.
6. Выйдите из старой сессии frontend и войдите созданным пользователем на
   http://localhost:3000.

Роли платформы:

- `viewer` — просмотр данных;
- `trader` — управление торговыми конфигурациями, ордерами и позициями;
- `admin` — управление пользователями, risk-настройками и служебными операциями.

Если изменить пароль bootstrap-администратора через Keycloak, обновите
`KEYCLOAK_ADMIN_PASSWORD` в `.env` и пересоздайте API Gateway, иначе управление
пользователями из интерфейса платформы перестанет работать:

```bash
docker compose up -d --force-recreate api-gateway
```

Пользовательские конфигурации и портфели привязаны не к username, а к неизменяемому
Keycloak user ID (`sub`). Не удаляйте пользователя и не пересоздавайте realm, если
за ним уже закреплены данные: новый пользователь с тем же именем получит другой ID
и не увидит старые конфигурации. Обычная смена пароля ID не меняет. Команда
`docker compose down` сохраняет данные, а `docker compose down -v` удаляет volumes
PostgreSQL, Redis и Keycloak — для рабочего окружения её использовать нельзя.

### Остановка и повторный запуск

```bash
docker compose stop
docker compose start
```

Для обновления после изменения исходного кода:

```bash
docker compose up -d --build --remove-orphans
```

## Сервисы

| Сервис | Назначение | Порт |
| --- | --- | --- |
| data-service | Закрытые свечи, рыночные данные, PostgreSQL | 8000 |
| elliott-service | Live-паттерны и сигналы Elliott | 8010 |
| decision-service | Отбор сигналов и риск-лимиты | 8020 |
| execution-service | Ордера, позиции, конфигурации и портфели | 8030 |
| analytics-service | Метрики и мониторинг | 8040 |
| api-gateway | Авторизация и маршрутизация REST/WebSocket | 8050 |
| exchange-gateway | Рыночные данные и история OKX | 8070 |
| backtest-service | Исторический replay Elliott | 8080 |

Инфраструктура: PostgreSQL/TimescaleDB, Redis и Keycloak.
PostgreSQL, Redis и прикладные микросервисы не публикуют порты на хост: доступ к ним
идёт только через Docker network. На loopback публикуются frontend, API и Keycloak,
чтобы перед ними можно было безопасно поставить TLS reverse proxy.

## Публичное развёртывание

Не публикуйте порты `3000`, `8050` и `8080` напрямую в интернет. Заполните случайные
`POSTGRES_PASSWORD`, `REDIS_PASSWORD`, `KEYCLOAK_ADMIN_PASSWORD`, публичные HTTPS URL
и hostnames из `.env.example`, затем запустите встроенный TLS ingress:

```bash
docker compose -f docker-compose.yml -f docker-compose.production.yml up -d --build
```

DNS-записи `FRONTEND_HOST`, `API_HOST` и `KEYCLOAK_HOST` должны указывать на сервер;
production overlay сам формирует из них HTTPS issuer, CORS allowlist и frontend URL,
а входящие TCP 80/443 — быть открыты для автоматического выпуска сертификатов Caddy.
API в production overlay откажется запускаться с HTTP issuer,
не-HTTPS CORS origin, wildcard Host или дефолтным административным паролем.
Публичный ingress не пропускает Keycloak Admin Console. Для первоначального создания
пользователя откройте SSH tunnel к `127.0.0.1:8080` на сервере и работайте с консолью
через этот tunnel; не меняйте bind address на `0.0.0.0`.

Перед включением `OKX_TRADING_ENABLED` создайте отдельный API key без права вывода
средств, ограничьте его IP-адресом сервера и сначала проверьте DEMO. Любые ключи,
которые когда-либо попадали в логи, терминал или чат, необходимо отозвать и создать заново.

Для OKX Demo заполните `OKX_API_KEY`, `OKX_SECRET_KEY`, `OKX_PASSPHRASE`, оставьте
`OKX_DEMO=true` и установите `OKX_TRADING_ENABLED=true`. После изменения `.env`
пересоздайте exchange gateway:

```bash
docker compose up -d --force-recreate exchange-gateway
curl http://localhost:8050/health
```

В интерфейсе активируйте торговую конфигурацию в режиме `DEMO`. Режим конкретного
актива (`PAPER`, `DEMO` или `PRODUCTION`) хранится в его торговой конфигурации;
`OKX_DEMO` определяет, к какому аккаунту подключён exchange gateway. Конфигурация
`PRODUCTION` не будет принята gateway, запущенным с `OKX_DEMO=true`, и наоборот.

## Работа с платформой

1. В «Конфигурациях» задайте таймфреймы Macro, Structure и Entry, модель входа
   Elliott, ATR/ZigZag, Stop Loss, цели Risk/Reward и параметры риска.
2. В «Бэктесте» выберите актив, загрузите историю OKX для нужных таймфреймов
   и задайте начало и конец тестового периода.
3. Запустите бэктест. Он использует сохранённые закрытые свечи и тот же детектор
   Elliott, что и live-сервис. Обучающего периода и ML-модели нет.
4. Откройте результат: кривая капитала, сделки, просадка, диагностика волн.
   Сохранённые запуски можно сравнить, выгрузить в CSV/JSON и открыть в Replay.
5. В «Рынке» просматривайте паттерны и сигналы активных конфигураций;
   в «Сделках» — ордера, позиции и результаты исполнения.

При запуске портфеля в live укажите общий live-капитал и режим капитала.
В `ALLOCATED` («Параллельно · фиксированные доли») капитал сразу делится между
активами: каждый торгует в пределах своей доли и накапливает собственный PnL.
Открытая позиция или незавершённая заявка запрещает новый вход только в тот же актив.
В `SEQUENTIAL` («Последовательно · общий капитал») одновременно разрешена одна
сделка; доля следующего актива считается от актуального общего капитала.
В параллельном режиме сумма долей не может превышать 100%; в последовательном
каждая отдельная доля может достигать 100%. Выбор применяется и к бэктесту, и к live.
Старые live-конфигурации и API-запросы без режима сохраняют последовательное
поведение. Для изменения режима нужно дождаться завершения активных сделок
и заново активировать портфель с выбранным режимом.
Для `DEMO` и `PRODUCTION` сумма не может превышать USDT equity подключённого OKX-аккаунта.
Активация не отправляет ордер сразу: ордера создаются по новым Elliott-сигналам.
После активации backend сам подписывается на нужные таймфреймы, догружает пустую
историю и внутренние пропуски, обрабатывает сигналы, заявки и выходы без открытого
браузера. Удаление актива из live немедленно запрещает новые входы; незавершённая
заявка отменяется, а открытая позиция закрывается reduce-only заявкой. Закрытие
может завершиться позже ответа API, если OKX или Redis временно недоступны.

Бэктест не отправляет ордера на биржу. `PAPER` исполняется внутри платформы без
биржевой заявки; `DEMO` и `PRODUCTION` отправляются через OKX только при включённом
`OKX_TRADING_ENABLED` и совпадающем значении `OKX_DEMO`.

## Ревью жизненного цикла реального портфеля — 22 октября 2026

### Вывод и границы проверки

**Текущий код не обеспечивает надёжную автономную торговлю на реальном счёте при
сбоях связи, частичных исполнениях и перезапусках.** Основной торговый цикл работает
без браузера, но обнаружены пути потери сигналов, зависания заявок, расхождения
локальных позиций с OKX и неправильного обновления капитала. До устранения
критических находок запуск новых реальных сделок нельзя считать проверенным.

Проверен код ревизии `dba8c38`: регистрация и активация портфеля, frontend/API,
сбор данных, Elliott, риск, исполнение, сопровождение, восстановление и аналитика.
Это ревью реализации и доступной локальной конфигурации, **не подтверждение
состояния работающего production-сервера**. Docker в среде проверки недоступен;
фактические контейнеры, таблицы production-БД, биржевые позиции и права ключа не
проверены. Реальные заявки не отправлялись, конфигурация торговли не изменялась.

В локальном `.env` обнаружены `OKX_DEMO=false`, `OKX_TRADING_ENABLED=true`,
`OKX_LIVE_MARKET_ENABLED=true`, `EXECUTION_MODE=paper` и
`EXCHANGE_TIMEFRAMES=M1,M5,M15,H1,H4,D1`. Отдельного `OKX_PRIVATE_WS_URL` в нём нет.
Это означает описанное ниже несоответствие при запуске данным Compose без внешнего
переопределения переменной. Секреты в отчёт не включены.

`EXECUTION_MODE=paper` не является общим предохранителем: фактический режим заявки
берётся из `trading_configs.mode`. Поэтому актив с `PRODUCTION` может торговать
реально, даже когда `/health` execution-service показывает `mode: paper`.
Production-overlay настраивает публичный ingress и авторизацию, но сам по себе
не переключает биржевое подключение и не проверяет готовность торгового цикла.

Приоритеты: **P0** — возможна неучтённая или незащищённая реальная экспозиция;
**P1** — нарушается исполнение, автономность, учёт или ограничение риска;
**P2** — эксплуатационная проблема, которая требует устранения для длительной работы.
Приоритет отражает последствия при указанном сценарии, а не утверждение, что он уже произошёл.

### Как система работает сейчас

| Этап | Фактическое поведение |
| --- | --- |
| Сохранение конфигурации | `strategy_configurations` хранит конфигурацию с владельцем. Сохранение ещё не включает торговлю. |
| Создание портфеля | `POST /portfolios` сохраняет активы, доли и копии конфигураций в `portfolios.assets`. Проверяется принадлежность конфигураций пользователю. |
| Активация | `POST /portfolios/{id}/live` проверяет сумму долей, подготавливает метаданные SWAP, проверяет режим OKX, права ключа, net position mode и USDT equity. |
| Запись live-настроек | Каждому символу записываются `mode`, `ACTIVE`, общий `initialCapital/currentCapital`, доля и `portfolioId`. Остальные активные конфигурации отключаются. Публикуется `trading.config.saved`. |
| Сбор рынка | exchange-gateway подписывается на свечи выбранных TF. Подписка на `trades` и `books5` включается отдельно через `OKX_RAW_MARKET_DATA_ENABLED=true`. Data-service сохраняет полученные сообщения в PostgreSQL и публикует Redis Pub/Sub. |
| Поиск входов | Elliott получает закрытую свечу entry-TF, загружает необходимые серии напрямую из OKX REST, вычисляет паттерн и план входа. Сохраняет `scenarios` и outbox, публикует `scenario.created`. |
| Сигнал и риск | decision-service выбирает сценарий, создаёт `trade_signals`, проверяет лимиты и размер, пишет `risk_decisions`, отправляет `risk.approved` в Redis Stream `trading.command`. |
| Регистрация заявки | execution-service создаёт `orders`. Для MARKET/LIMIT в DEMO/PRODUCTION публикует `order.request` в `execution.command`. STOP ожидает пересечения уровня локально по M1, затем превращается в MARKET. |
| Отправка на биржу | exchange-gateway переводит базовое количество в контракты, округляет размер/цену, устанавливает плечо, добавляет TP/SL, отправляет REST-заявку и сохраняет `exchange_orders`. |
| Открытие позиции | По приватному WebSocket приходит фактическое исполнение. Через `trading.command` execution-service обновляет заявку, создаёт/увеличивает `positions`, ведёт `position_state_history` и Redis `positions:open`. |
| Сопровождение | В PRODUCTION исходные SL/TP передаются бирже. M1 используется для цены, локального STOP-входа, срока заявки и переноса SL в безубыток. Локального резервного исполнения SL/TP для PRODUCTION нет. |
| Выход | Исполнение защитной заявки уменьшает позицию. Ручное закрытие отправляет reduce-only MARKET и ожидает фактический fill. При полном закрытии создаётся `closed_trades`, обновляется капитал и публикуется `position.closed`. |
| Следующая сделка | decision-service по событию закрытия/отмены/отказа освобождает резерв и повторно проверяет ожидающие сигналы. |

При активации ордер немедленно не отправляется. Анализ стартует от следующих
рыночных событий; при этом может быть выбран ранее сформированный паттерн, если
его срок входа ещё действует. Фильтра «сигнал возник только после активации» нет.

Торговля намеренно последовательная: **одна активная заявка или позиция на всю
систему**, включая разные активы и режимы. `max_positions > 1` этого не меняет:
в risk-manager используется `min(config.max_positions, 1)`. Доли портфеля
ограничивают размер отдельной сделки, но не создают параллельные позиции.
Длительно висящая заявка блокирует весь портфель.

Frontend можно закрыть после активации: чтение рынка, сигналы и заявки выполняют
серверные задачи. Исключение — описанная в R15 автоматическая загрузка исторического
датасета и исторического отображения: её часть сейчас находится во frontend.

### Существенные ошибки и сценарии отказа

#### R01 — P0. Реальные REST-заявки при демонстрационном приватном WebSocket

Compose и `Settings` по умолчанию задают приватный адрес `wspap.okx.com`, независимо
от `OKX_DEMO`. В проверенном `.env` режим реальный, но адрес не переопределён.
REST использует `OKX_DEMO=false`, а приватный WebSocket пытается работать с Demo.
Проверка активации использует REST и не проверяет успешную подписку на приватные события.
`place_order()` также не ждёт готовности приватного канала.

**Последствие:** активация может пройти, реальная заявка уйдёт на OKX, но её fill
не попадёт в локальную позицию. Заявка останется `OPEN/SUBMITTING`, сопровождение
и следующие сделки могут остановиться. Это не утверждение о текущем сервере:
внешнее переопределение URL могло бы устранить именно конфигурационную часть.

Исправление: выбирать и валидировать endpoint по режиму, требовать подтверждённую
подписку и первоначальную сверку состояния перед разрешением новых заявок.
Production URL для глобального подключения: `wss://ws.okx.com/ws/v5/private`.
См. [Compose](docker-compose.yml),
[settings.py:10](services/exchange-gateway/src/settings.py),
[service.py:281,430](services/exchange-gateway/src/service.py).
Разделение адресов подтверждено [документацией OKX](https://www.okx.com/docs-v5/).

#### R02 — P0. Нет сверки с биржей после разрыва связи и неопределённого результата REST

После переподключения private-loop только заново подписывается на `orders`.
Не запрашиваются реальные позиции, активные/исторические заявки, исполнения и
защитные algo-заявки. Входящие события чужих/manual/ликвидационных операций,
не связанных с собственными идентификаторами, также не формируют сверку позиций.
OKX не отдаёт первоначальный снимок ордеров при подписке на этот канал:
см. [официальное описание](https://www.okx.com/docs-v5/trick_en/).

Дополнительно любой сбой `place_order()`, включая timeout после принятия заявки
биржей, превращается в `REJECTED` и подтверждается в очереди. При таком timeout
результат на бирже неизвестен, но система считает торговый слот освобождённым.
Повторная отправка тоже не защищена полноценно: `ON CONFLICT DO NOTHING` для
`exchange_orders` не предотвращает сам повторный REST POST.

**Последствие:** пропущенный вход/выход не восстанавливается; возможны неучтённая
позиция, ложный отказ или новая сделка поверх реально существующей экспозиции.
Исправление: состояние `UNKNOWN`, поиск по `clOrdId`, reconciliation при старте,
reconnect и периодически; запрет новых входов до разрешения расхождений.
Источник: [exchange service.py:281–326,340–371,430–460,700–720](services/exchange-gateway/src/service.py).

#### R03 — P0. Частично исполненный вход может оставаться без активной защиты

Защита передаётся через `attachAlgoOrds`; отдельная защита фактически исполненной
части до завершения входной заявки не создаётся. В execution-service
`PARTIALLY_FILLED` исключён из проверки срока заявки, поэтому остаток не снимается
по `expires_at`. Для PRODUCTION ветка `on_candle()` не исполняет структурный стоп
локально — она рассчитывает на биржевую защиту.

По [обновлению OKX от 1 июля 2026](https://www.okx.com/en-au/help/okx-announcement-on-optimizing-order-placement-for-order-attached-take)
обычный attached TP/SL ставится после полного fill либо частичного fill с отменой
остатка; для Split TP требуется полный fill. Поэтому защиту частично исполненного
и всё ещё открытого входа считать установленной нельзя. Отмена остатка не решает
случай Split TP автоматически.

**Последствие:** частичная позиция уже реальна, а исходный стоп может ещё не
существовать на бирже. Исправление: подтверждать защиту каждой фактической позиции,
обрабатывать срок частичных входов и отдельно управлять остатком заявки.
Пропуск expiry воспроизведён офлайн.
Источники: [execution service.py:314–364](services/execution-service/src/service.py),
[exchange service.py:45–87,449–452](services/exchange-gateway/src/service.py).

#### R04 — P1. Состояния заявки могут откатываться и терять фактический fill

Подтверждены три разных перехода:

- После `FILLED` позднее сообщение `OPEN` безусловно возвращает заявку в `OPEN`.
  Это возможно, поскольку gateway самостоятельно публикует `OPEN` после REST ACK,
  параллельно получая `FILLED` по WebSocket. После закрытия позиции такой ордер
  продолжит занимать общий торговый слот.
- `CANCELLED` с ненулевым `filled_quantity` только меняет статус: накопленный fill
  не применяется. Если предыдущий partial-event пропущен, позиция отсутствует или занижена.
- Отмена `SUBMITTING` без `exchange_order_id` выполняется только локально.
  Команда размещения уже может находиться в очереди/обработке и после локального
  `CANCELLED` всё равно открыть реальную сделку.

Исправление: монотонная машина состояний, обработка cumulative fill для всех
финальных состояний, отмена по устойчивому `clOrdId` и проверка перед отправкой.
Все три случая воспроизведены офлайн.
Источник: [execution service.py:431–492](services/execution-service/src/service.py).

#### R05 — P1. Сохранение заявки и отправка команды не атомарны

`create_order()` помещает заявку в память и БД, переводит в `SUBMITTING`, а затем
выполняет `XADD`. При сбое Redis между этими действиями заявка остаётся активной,
хотя команда не отправлена. Повторная обработка того же сигнала завершается
дедупликацией по `signal_id` и не повторяет отправку. Аналогичные окна есть при
локальном STOP-входе, запросе закрытия и запросе переноса защиты.

**Последствие:** зависание общего торгового слота; после crash на записи
`protection_pending=true` защита также может навсегда остаться «в обработке».
Исправление: транзакционный outbox команд, повторная доставка и идемпотентные
получатели; восстановление промежуточных состояний по журналу.
Потеря отправки и бесполезный повтор воспроизведены офлайн.
Источник: [execution service.py:151–193,298–323](services/execution-service/src/service.py).

#### R06 — P1. Очереди не обеспечивают восстановление обработки

Gateway создаёт группу `execution.command` с `id="$"`: при первом запуске consumer
пропускает уже существующие команды. Затем читает только `>` и не возвращается
к pending-сообщениям после аварийного завершения. Ошибка `xreadgroup` вне внутреннего
`try` завершает задачу навсегда; автоматического перезапуска этой задачи нет.

Execution-service читает pending только один раз при старте и только для своего
consumer name. Ошибки дальнейшей обработки остаются в pending до следующего старта;
`XAUTOCLAIM`/периодического recovery нет. Ошибка самого начального чтения pending
может завершить consumer до перехода в защищённый цикл.

**Последствие:** команды открытия, закрытия и защиты могут не исполняться при
живом HTTP-сервисе. Исправление: корректная начальная позиция группы, регулярный
pending recovery, контроль попыток и supervision фоновой задачи.
Источники: [exchange service.py:153–154,340–371](services/exchange-gateway/src/service.py),
[execution service.py:114–142](services/execution-service/src/service.py).

#### R07 — P1. Закрытие позиции и финансовый результат могут сохраниться частично

`close()` сначала изменяет количество/PnL в памяти, затем снимает Redis-маркер,
сохраняет `CLOSED`, пишет `closed_trades`, обновляет капитал и публикует событие.
Общей транзакции нет. Если запись результата упала после `CLOSED`, повторный
protective fill уже не найдёт открытую позицию и пропустит восстановление.
У `closed_trades` случайный UUID записи, а не уникальный ключ завершения позиции.
Обновление капитала нескольких символов также выполняется отдельными запросами.

**Последствие:** позиция закрыта, но сделки в истории/PnL нет, капитал устарел,
ожидающие сигналы не разблокированы или активы используют разные значения капитала.
Исправление: транзакция позиции, результата и капитала; устойчивый идентификатор
закрытия; outbox событий. Потеря результата после `CLOSED` воспроизведена офлайн.
Источник: [execution service.py:198–217,406–429](services/execution-service/src/service.py).

#### R08 — P1. Сигналы и освобождение торгового слота теряются при недоступности decision-service

Outbox Elliott отмечается опубликованным после Redis `PUBLISH`, независимо от
того, получил ли сообщение decision-service. Pub/Sub не является сохраняемой
очередью. При недоступном получателе сценарий остаётся в БД, но не обрабатывается.
Восстановление ACTIVE-сценариев дополнительно сломано: используется
`Scenario.model_validate(row["data"])`, хотя стандартный asyncpg возвращает JSONB
строкой; ошибка ловится и сценарий пропускается. Даже после исправления декодирования
загрузка в словарь сама по себе не запускает `resolve()`.

WAITING-сигналы при старте только загружаются. Повторная оценка привязана к Pub/Sub
`position.closed/order.cancelled/order.rejected`; периодического запуска нет.
Если событие пропущено работающим decision-service, `reserved_signal_id` не
освобождается, и последующие сигналы тоже могут оставаться в WAITING.
Между записью `APPROVED` и `XADD risk.approved` также нет outbox.

**Последствие:** рынок продолжает поступать, но заявки перестают появляться.
Исправление: сохраняемая доставка сценариев, startup/periodic recovery всех
нетерминальных сигналов, резерв в БД с проверкой реального состояния.
Ошибка декодирования воспроизведена офлайн.
Источники: [elliott service.py:40–48](services/elliott-service/src/service.py),
[decision service.py:33–55,66–76,95–119,125–186](services/decision-service/src/service.py).

#### R09 — P1. Идентификаторы паттернов конфликтуют между активами

`pattern.id` вычисляется как UUID от направления и трёх времён P0/P1/P2.
Символ, TF и версия конфигурации отсутствуют. Live-engine использует общий
`emitted`, а `scenarios.id` — глобальный primary key. Если коррелирующие активы
сформируют одинаково направленные точки на тех же свечах, ID совпадёт.

**Последствие:** второй актив теряет сценарий как дубликат; после рестарта
подавление сохраняется, поскольку emitted восстанавливается из БД.
Исправление: отделить локальный pattern ID от live scenario ID, включить в
последний символ, TF и согласованную область конфигурации/активации.
Источники: [elliott.py:188–189](services/backtest-service/src/elliott.py),
[elliott_live.py:213–218,284–304](services/elliott-service/src/elliott_live.py),
[elliott service.py:65–71,273–281](services/elliott-service/src/service.py).

#### R10 — P1. Переключение портфеля не согласовано с действующими сделками

Live-конфигурации глобальны и имеют ключ только `symbol`. Активация портфеля
отключает ВСЕ остальные активные конфигурации, без фильтра владельца/портфеля.
Проверки активных заявок и позиций на этом пути нет. При этом сделки не закрываются,
очереди не очищаются, а на совпадающих символах перезаписываются режим и капитал.
Повторная активация сбрасывает `currentCapital` на введённую сумму.

`update_current_capital()` определяет портфель через текущий config символа,
а не через `position.portfolio_id`. После переключения PnL старой сделки может
попасть в новый портфель либо не обновить капитал, если символ отключён.
`on_approved()` тоже читает текущий режим/config: старое одобрение может быть
исполнено уже в новом портфеле или режиме. Удаление сохранённого портфеля
не отключает его live-конфигурации.

**Последствие:** влияние пользователей/портфелей друг на друга и неправильное
присвоение финансового результата. Даже для одного пользователя опасно переключение
PAPER → PRODUCTION при незавершённых командах.
Исправление: явная сущность live-запуска, неизменяемый scope сигнала/заявки,
контролируемая остановка/переключение и учёт по исходному запуску позиции.
Источники: [execution app.py:196–246](services/execution-service/src/app.py),
[execution service.py:151–164,198–217](services/execution-service/src/service.py).

#### R11 — P1. Просроченный сигнал может уйти на биржу после задержки

Срок проверяется при выборе сценария, но не повторно в `on_approved()`,
`create_order()` и `place_order()`. Задержанная `risk.approved` способна создать
и отправить уже просроченный MARKET/LIMIT. Проверка expiry выполняется позже по
времени поступившей свечи, а не обязательной проверкой часов перед отправкой.
При остановке потока свечей локальные expiry и STOP вообще не срабатывают.

Исправление: проверять срок, возраст данных и актуальность live-запуска на каждой
границе исполнения; иметь серверный таймер отмены, независимый от рынка.
Приём просроченного одобрения воспроизведён офлайн.
Источники: [execution service.py:151–180,314–323](services/execution-service/src/service.py),
[exchange service.py:430–457](services/exchange-gateway/src/service.py).

#### R12 — P1. Реальный риск и капитал расходятся с утверждёнными значениями

- Risk-manager ограничивает плечо глобальным лимитом, но execution-service
  заменяет одобренное плечо значением конфигурации. Воспроизведено: одобрено `1`,
  заявка получает `20`. Размер остаётся ранее рассчитанным, но фактическая маржа
  и условия ликвидации уже иные.
- Биржевая equity проверяется при активации. Перед обычным сигналом нет сверки
  текущего доступного баланса; используется локальный `currentCapital` и
  `capital_ceiling=None`. Пополнения, выводы, внешние сделки и расхождения не учитываются.
- Фактические комиссии и funding из биржевого учёта не применяются к PnL.
  Комиссия LIMIT считается maker даже при taker-исполнении; ставка превращается
  в `abs()`, теряя знак rebate. Funding начисляется только PAPER-веткой.
- Метаданные fee/funding обновляются при refresh, но не по расписанию;
  `prepare_instruments()` не загружает их для новых активов. Live Elliott
  подставляет нули при отсутствующих значениях. Daily loss считается по последним
  100 закрытым сделкам, а не по всем сделкам дня.
- Live-sizing использует текущий капитал независимо от `reinvestProfits`, тогда
  как replay различает этот режим. Прибыль способна увеличивать live-размер даже
  при выключенном реинвестировании.

Исправление: исполнять одобренные параметры; сверять баланс/позиции/комиссии/funding
с OKX, отделить выделенный капитал от equity счёта, согласовать live и replay.
Источники: [decision service.py:138–174](services/decision-service/src/service.py),
[risk.py:38–49](services/decision-service/src/risk.py),
[execution service.py:159–164,254,340–371,406–429](services/execution-service/src/service.py),
[exchange service.py:183–264](services/exchange-gateway/src/service.py),
[elliott service.py:229–232](services/elliott-service/src/service.py).

#### R13 — P1. Healthcheck не подтверждает работоспособность торговли

Exchange `/health` всегда возвращает HTTP 200 и `UP`, даже при отсутствующем
приватном соединении. Состояние сокетов выставляется до подтверждения login/subscribe;
ошибка авторизации не превращается в запрет новых REST-заявок.
Execution/decision/Elliott проверяют доступность БД/Redis, но не живость consumer,
возраст последней свечи, pending-команды или расхождение с биржей.

**Последствие:** Docker/мониторинг показывают healthy, а торговая задача завершилась
или данные устарели. `restart: unless-stopped` не перезапускает отдельную погибшую
async-задачу и не исправляет ложный HTTP 200.
Исправление: отдельная trading-readiness, task supervision, heartbeat, метрики
задержек/расхождений и блокировка новых входов при деградации.
Источники: [exchange app.py:34–35](services/exchange-gateway/src/app.py),
[exchange service.py:153–174,281–297](services/exchange-gateway/src/service.py),
[execution app.py:94–97](services/execution-service/src/app.py),
[decision app.py:14–17](services/decision-service/src/app.py).

#### R14 — P1. Запланированное отключение порта WebSocket 8443

В Compose, `.env.example` и настройках gateway используются адреса с `:8443`.
По [официальному changelog OKX](https://www.okx.com/docs-v5/log_en/#upcoming-changes-websocket-port-8443-discontinuation)
подключения через публичный интернет на этот порт перестанут приниматься
**31 октября 2026 года**. На дату ревью это предстоящая, а не уже случившаяся поломка.

**Последствие:** перестанут приходить свечи и приватные исполнения. Нужно убрать
`:8443` или явно использовать `:443` во всех effective URL, одновременно исправив
Demo/Production host из R01. REST этим изменением не затрагивается, что особенно
опасно без запрета отправки при неисправном private-channel.
Источники: [Compose](docker-compose.yml), [settings.py:7–10](services/exchange-gateway/src/settings.py).

#### R15 — P1. Историческая догрузка не полностью автономна; entry-TF может отсутствовать

Активация портфеля подготавливает инструменты и подписки, но не создаёт history-job
для заполнения PostgreSQL. При пустой истории snapshot получает `WAITING_FOR_DATA`.
Запрос догрузки за 180 дней делает React-effect страницы «Рынок». Если страницу
не открыть, он не выполнится. Для роли trader этот запрос дополнительно запрещён
gateway: запись `/exchange/history` разрешена только admin.

При этом live-анализ не обязан ждать PostgreSQL: он сам читает историю OKX REST
в память. Поэтому «нет локального датасета» и «нет live-сигналов» — разные состояния.
Исторический snapshot автоматически не пересчитывается на каждой новой свече.

Отдельный блокер: TF подписки задаются статическим `EXCHANGE_TIMEFRAMES`, а не
набором активных конфигураций. В проверенном `.env` и `.env.example` отсутствует M30.
Если entry-TF=M30, событие для запуска live-анализа не придёт; допустимая конфигурация
будет ACTIVE, но сигналы не появятся. REST-догрузка не помогает: она вызывается
только при событии entry-TF.

Исправление: backend warm-up/backfill и readiness датасета; формирование подписок
из активных конфигураций плюс обязательный M1; явная проверка поддержки TF.
Источники: [market/page.tsx:107–118,163–173](frontend/app/market/page.tsx),
[security.py:147–157](services/api-gateway/src/security.py),
[elliott service.py:139–158,246–266](services/elliott-service/src/service.py),
[exchange service.py:156–169](services/exchange-gateway/src/service.py).

#### R16 — P1. Свеча текущей минуты может использовать экстремум до создания заявки

`actionable_candle()` допускает свечу, если конец её минуты позже `created_at`.
Execution обрабатывает и незакрытые обновления. Пример: high=110 сформировался
в 12:00:05; STOP BUY=105 создан в 12:00:40, когда цена уже 100. Обновление той же
минутной свечи с историческим high=110 отправит MARKET, хотя после создания заявки
уровень ещё не пересекался. Аналогично возможен преждевременный перенос в безубыток.

Исправление: для real-time trigger использовать свежие тики/ценовые переходы после
времени создания или явно исключать неоднозначную первую свечу. Проверка M1 вместо
старших TF уменьшает проблему, но не устраняет её внутри минуты.
Источник: [execution service.py:14–17,314–357](services/execution-service/src/service.py).

#### R17 — P2. Активация не валидирует всю стратегию и зависит от порядка создания таблиц

`TradingConfigCreate` проверяет только несколько числовых полей и название стратегии;
`validate_live_config()` — только тип объекта `elliott`. Полная валидация
`BacktestConfig` выполняется позже в анализаторе. Некорректная конфигурация,
переданная через API, может стать ACTIVE, но не генерировать сигналы.

На чистой БД execution-service при старте делает JOIN `exchange_orders`, которую
создаёт gateway; gateway изменяет `trading_assets`, создаваемую backtest-service.
Соответствующих зависимостей запуска в Compose нет. Restart-policy может дать
восстановиться позднее, но первоначальный запуск зависит от гонки сервисов.

Исправление: единая валидация конфигурации до активации, централизованные миграции
схемы до старта потребителей. Источники:

### Хранение, обновление и применение свечей и связанных данных

Этот раздел описывает **ограничения в коде**, а не измеренный объём production-БД.
Количество фактически накопленных строк и размер файлов без доступа к серверу
не установлены. PostgreSQL и Redis сохраняются в Docker volumes; Redis включён
с AOF. Перезапуск контейнера не является очисткой этих данных.

#### Что и сколько хранится

| Данные | Где и ключ | Глубина/очистка в текущей реализации | Где используются |
| --- | --- | --- | --- |
| Свечи | PostgreSQL/TimescaleDB `candles`, `(symbol,timeframe,ts)` | Автоматического срока хранения и ограничения числа строк нет; есть ручное удаление датасета | Графики, backtest, исторический replay, стартовый кэш Elliott |
| Рыночные сделки | `market_ticks`, `(symbol,trade_id,ts)` | При `OKX_RAW_MARKET_DATA_ENABLED=true` хранятся до 6 часов с округлением до границ чанков | Market API, поток событий; сами по себе не запускают Elliott-сигнал |
| Стакан books5 | `order_books`, `(symbol,ts)`; bids/asks JSONB | При `OKX_RAW_MARKET_DATA_ENABLED=true` снимки хранятся до 2 часов с округлением до границ чанков | API последнего стакана и события; не основной источник Elliott |
| Метаданные актива | `trading_assets`, ключ `symbol` | Одна актуальная запись: tick/lot/min-size/contract-value, fee/funding, exchange_metadata | Проверка и округление заявки, sizing и настройки анализа |
| Сценарии и решения | `scenarios`, `elliott_scenario_outbox`, `trade_signals`, `risk_decisions`, `decision_log` | Автоматической очистки не найдено | Дедупликация, риск, связь сигнала со сделкой |
| Заявки/позиции/сделки | `orders`, `exchange_orders`, `positions`, `closed_trades`, `position_state_history`, `live_trading_logs` | История в БД не ограничена; ограничения API/стартовой выборки не удаляют строки | Исполнение, сопровождение, отчёты |
| Общий журнал событий | TimescaleDB `event_store`, `(message_id,event_ts)` | Без автоматической очистки; текущая версия не дублирует рыночные события data-service | Аналитика/мониторинг; не журнал гарантированной доставки команд |
| Обычный кэш Elliott | Память процесса, `(symbol,timeframe)` | Последние **500** свечей на пару, по timestamp | Стартовое восстановление, отображение/пересчёт; при обычном live-входе используется отдельный REST-кэш |

| История загрузок | `exchange_history_jobs`, курсоры и статусы по TF | Сохранение прогресса и возобновление RUNNING как QUEUED после старта | Управляемый импорт истории, pause/resume/cancel |
| Результаты backtest | `backtest_runs`, JSON request/result | Завершённые/ошибочные/отменённые корневые запуски старше **48 часов** удаляются при старте и каждые **60 секунд**; дочерние удаляются каскадно | Сравнение и экспорт отчётов. Это очистка отчётов, не свечей |
| Команды Redis | Streams `trading.command`, `execution.command` | `MAXLEN ~100000` сообщений на stream; не срок хранения в днях | Риск, отправка, исполнения и защита; восстановление ограничено ошибками R05–R08 |

| События Redis Pub/Sub | `candle.update`, `scenario.update`, `position.update` и др. | Не сохраняются для отсутствующих подписчиков | Запуск анализа, уведомления и разблокировка ожидающих сигналов |

Для локального набора M1/M5/M15/H1/H4/D1 теоретически добавляется **1855 новых
временных свечей на актив в сутки** при непрерывном покрытии, около **677 075 в год**.
Если включить M30 — 1903 в сутки. Обновления незакрытой свечи увеличивают число
операций записи, но не число строк `candles`. Текущая версия не сохраняет эти
обновления в `event_store`. Размер в GB зависит от тиков/стаканов, индексов,
WAL и числа активов; выводить его только из количества свечей некорректно.

По умолчанию `OKX_RAW_MARKET_DATA_ENABLED=false`: gateway не подписывается на OKX
`trades` и `books5`, но продолжает получать свечи для торговой логики. Для истории
каждой рыночной сделки можно включить настройку; Flyway V2 задаёт сроки хранения
тиков 6 часов и стаканов 2 часа, интервал новых чанков 1 час. Данные могут жить
дольше указанного срока, пока их чанк содержит более свежие записи. Старые чанки
с прежним интервалом не разделяются этой миграцией.

В режиме автономной торговли live Elliott загружает серии свечей из OKX REST в
собственный кэш памяти. При этом закрытая свеча из потока gateway запускает
пересчёт, а execution-service использует `candle.update` для локальных стоп-заявок.
Исторические свечи в PostgreSQL отдельно нужны для backtest, графиков,
восстановления после рестарта и поиска пропусков. Поэтому очистка по статусу
сигнала здесь не применяется; глубину хранения свечей следует выбирать исходя
из нужного диапазона backtest и исторического просмотра.

Исторический импорт свечей теперь отправляет пакетную запись в PostgreSQL;
повторная загрузка неизменившихся свечей не создаёт лишних UPDATE и WAL.
Пересчёт Elliott выбирает последние свечи отдельно по каждому таймфрейму,
не перебирая полную историю оконной функцией.

Чтобы определить источник занятого места на развёрнутой БД, выполните из корня
проекта (команда только читает данные):

```bash
docker compose exec -T postgres sh -lc 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < scripts/db_storage_diagnostics.sql
```

Если основную часть занимают `market_ticks` и `order_books`, а их история не нужна,
после резервной копии можно освободить её разово. Следующая команда **удаляет все**
сырые рыночные сделки и снимки стакана; свечи, торговые сделки и настройки остаются:

```bash
docker compose exec postgres sh -lc 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "TRUNCATE market_ticks, order_books;"'
```

Если велик `event_store`, проверьте дату развёртывания исправления фильтра рыночных
событий и размер отдельных чанков прежде, чем удалять историю. Файлы `pg_wal`
вручную удалять нельзя. При полностью заполненном диске сначала остановите
`exchange-gateway` или увеличьте доступное место, затем запускайте миграцию.

#### Как обновляется свеча

1. OKX присылает обновления по отдельным TF; собственная агрегация M1 → H1/H4
   в системе не реализована. `timestamp` — начало интервала, признак `is_closed`
   берётся из OKX `confirm`.
2. Gateway отправляет каждое обновление data-service. `INSERT ... ON CONFLICT`
   перезаписывает OHLCV и `is_closed` для одинаковых symbol/TF/time.
3. Data-service публикует `candle.update` для каждого одиночного ingest, включая
   незакрытые и повторные обновления. Elliott анализирует только закрытые;
   execution использует и текущие M1 для сопровождения.
4. Закрытая свеча не защищена от последующей записи более старого незакрытого
   обновления: проверки монотонности `is_closed`/версии нет. Также Redis-событие
   публикуется внутри DB-транзакции до её завершения, а не транзакционным outbox.
   Возможны событие до commit и расхождение публикации с сохранением.
5. Нормализатор gateway сохраняет `volume=item[5]`, но не передаёт `quote_volume`
   и `trades_count`. Их колонки допускают NULL. Не следует считать эту таблицу
   полным необработанным ответом биржи или без проверки интерпретировать объём
   SWAP как базовое количество актива.

#### Сколько данных реально применяет анализ

Для live Elliott целевое окно на каждый TF вычисляется так:

```text
min(200000, max(500, ceil(500 * длительность_macro_TF / длительность_этого_TF)))
```

При стандартных H4/H1/M15 это **500 H4, 2000 H1 и 8000 M15**, примерно 83 суток.
С entry=M1 и macro=H4 потребуется 120 000 M1. После холодного старта данные
загружаются страницами по 300; для стандартного набора получается примерно 36
запросов до учёта повторов. Далее загружаются свежие страницы, объединяются с кэшем,
удаляются дубликаты и проверяется непрерывность нужного окна.

Слишком молодой инструмент или пробел в требуемой истории даёт
`OkxMarketDataUnavailable`; сигнал на этом событии не создаётся. Загрузка и
вычисление выполняются в последовательном обработчике событий Elliott: задержка
одного актива задерживает последующие сообщения других активов. Готовность полного
окна до активации не проверяется. REST-кэш не пополняет PostgreSQL, поэтому наличие
данных для live не означает наличие тех же свечей в локальном backtest.

Исторический snapshot читает закрытые свечи из БД с похожим лимитом окна и строит
изолированный PAPER-replay. Он запускается при старте/сохранении конфигурации,
завершении загрузки истории или явном rebuild. Обычное поступление новых свечей
не обновляет snapshot постоянно. Backtest читает закрытые свечи из PostgreSQL
за диапазон с лимитом до `MAX_CANDLES` (по умолчанию **2 000 000** на TF).
HTTP Market API возвращает по умолчанию 500, максимум 10 000 свечей за запрос;
это лимит ответа, а не хранения.

#### Догрузка, пропуски и расхождение отображения с live

History-job получает страницы по 300 свечей, сохраняет только закрытые записи
через batch-ingest, сохраняет курсор и после завершения вызывает Elliott rebuild.
Batch-ingest намеренно не публикует каждую историческую свечу как live-событие,
а rebuild использует `allow_live_emit=False`. История поэтому не должна массово
отправлять старые сигналы в торговлю. Лимит `MAX_CANDLES` backtest не ограничивает
объём такой загрузки: история ограничивается заданным диапазоном/доступностью OKX.

При разрыве рыночного WebSocket соединение восстанавливается, но **автоматического
ремонта пропусков в PostgreSQL нет**. `incremental` начинает с максимального
сохранённого timestamp плюс один интервал. Если после разрыва уже записалась новая
свеча, пропуск внутри диапазона incremental не заполнит. `backfill` загружает
период раньше минимального timestamp, а не внутренние разрывы. Есть API аудита
датасета, но он не включён в автоматический цикл контроля и ремонта.

У страницы графика есть собственное чтение свежих свечей из OKX с кэшем gateway
(10 секунд для свежей страницы и 600 секунд для исторической). Это тоже не
сохраняет их в `candles`. Поэтому визуально полный график не доказывает полноту БД.
Кроме того, UI при наличии `COMPLETED` historical snapshot предпочитает его
паттерны: старый снимок может выглядеть как текущее состояние анализа.

Ручное удаление датасета удаляет общие строки `candles` по символу/TF без проверки
активной live-конфигурации и без сброса всех кэшей. До перезапуска live может
продолжить работу из REST/памяти, тогда как локальные отчёты уже лишены истории.
Отключение `trading_assets.enabled` также не является согласованной остановкой
торговли: подписки обновляются отдельно, а запрос Elliott config не фильтрует enabled.

Для надёжной автономной эксплуатации нужны backend-проверка покрытия и свежести,
ремонт внутренних пропусков, единые правила финализации свечей, контроль источника
данных в отчётах, подтверждённая остановка при отключении актива и явная политика
хранения. Изменения по этим пунктам в рамках ревью не внесены.

история, таймфреймы и остановка актива обрабатываются backend. Финальное закрытие
позиции, результат и капитал записываются в одной транзакции.
Перед новым входом проверяется свежая M1-свеча именно этого актива.

Ручное добавление актива подготавливает биржевые метаданные и проверяет
доступный капитал так же, как запуск портфеля. Отключение запрещает новые входы
сразу; существующую биржевую позицию backend закрывает заявкой reduce-only.

Кодовые исправления не означают допуск к реальным заявкам: остаются точная сверка
комиссий и funding с биржевыми начислениями, политика хранения старой истории и
проверка полного цикла на OKX Demo с разрывами связи и перезапусками. При
неразрешённом расхождении с OKX новые входы блокируются до сверки; локальные данные
не подменяются приблизительным финансовым результатом.
